# J-MoshiVis Dataset Viewer

J-MoshiVis のデータ構築状況を、画像・対話・音声・アライメントの順に確認するための Web ビューアです。画像や音声をコピーせず、既存データをカタログ化して同一オリジンから必要な1件だけ配信します。元の画像・対話・音声・アライメントは変更せず、必須・任意を問わず人手による編集・承認履歴を独立した追記専用 JSONL に保存します。

## 起動

リポジトリ直下で、プロジェクトのデータ処理用 Python 環境を使って起動します。

```bash
.venv-data/bin/python -m dataset_viewer.app_daily
```

既定の待受先は `127.0.0.1:8765` です。初回起動時は画面を先に表示し、バックグラウンドでカタログを作成します。既存カタログがあれば、その内容をすぐ表示したまま差分を確認します。

現在の約20.7万論理 UID では、初回索引はこのサーバーで約2分、SQLite
キャッシュは約725 MBでした。2回目以降は変更されたJSONLだけを再取込します。
GPU/CUDAは読み込まず、実行中の学習・VLM生成処理とは独立してCPUで動作します。

```bash
# ポートまたは保存先を変更
.venv-data/bin/python -m dataset_viewer.app_daily \
  --host 127.0.0.1 --port 8765 \
  --db data/.dataset_viewer/catalog.sqlite3 \
  --refresh-interval 10

# 入力をすべて走査し直す（元データは変更しない）
.venv-data/bin/python -m dataset_viewer.app_daily --rebuild
```

サーバー上で実行し、手元のブラウザから見る場合は SSH トンネルを張ります。

```bash
ssh -N -L 8765:127.0.0.1:8765 USER@SERVER
```

その後、手元のブラウザで <http://127.0.0.1:8765> を開きます。共有ネットワークへ公開する必要がある場合だけ `--host 0.0.0.0` を指定し、サーバー側のアクセス制御も併用してください。

## 対象コレクション

| コレクション | 主な入力 | 用途 |
|---|---|---|
| 画像対話 v3 (`visual_v3`) | `data/dialogues_merged/dialogues_final_v3.jsonl`, `data/speech_v3/` | 一般画像に基づく対話 |
| 日本の日常画像 v1 (`japanese_daily_v1`) | `data/images/japanese_daily_v1/accepted_images.jsonl`, `data/dialogues_japanese_daily_v1/full/qwen3vl_30b_normal_adaptive.jsonl` | 採用済み画像と生成中の対話を同じ UID で結合して表示 |
| カウント画像 v4 (`counting_v4`) | `data/images/targeted_v4/image_pool_v1/counting_images.jsonl`, `data/dialogues_counting/full/` | 人数・物体数を数える対話（構築中を含む） |
| 日本語 OCR 画像 v4 (`ocr_v4`) | `data/images/targeted_v4/image_pool_v1/ocr_images.jsonl` | 店名・看板などの日本語文字認識（構築中を含む） |
| 非画像対話 v1 (`nonvisual_v1`) | `data/dialogues_nonvisual/claude_sonnet5_nonvisual_tts_v1.jsonl`, `data/speech_nonvisual_v1/` | 画像に依存しない対話 |

コレクション内の **1件** は、一意な `(collection, UID)` です。ダッシュボードは `visual_v3`・`japanese_daily_v1`・`counting_v4`・`ocr_v4` を「画像付きデータ」、`nonvisual_v1` を「非画像対話データ」として分けて表示します。「総音声」は両者を合算した音声 UID 数と総再生時間です。「画像」「対話」「音声」「アライメント」はファイル数や発話ターン数ではなく、それぞれの工程に到達した UID 数です。同じ UID に複数ターン、複数メタデータファイルがあっても1件として数えます。この定義により、各データ種別を混ぜずに工程間の不足数を比較できます。

`japanese_daily_v1` の `accepted_images.jsonl` に入った画像は、学習用画像バンクへの採用が確定したものです。ただし、Web上の「学習サンプル完成」は対話・音声・アライメントまで揃った状態を指します。収集中は `画像あり／対話なし` と表示し、マニフェストの追記分だけを差分索引します。

## 操作

- 右上の「データ閲覧／アノテーション」で画面を切り替えます。アノテーション画面への直接リンクは <http://127.0.0.1:8765/#annotate> です。通常の進捗カード・ディレクトリツリーを省き、承認系のダッシュボードを最上部に置きます。画像と対話を左右に大きく表示し、画像・対話・メモ・編集・承認は通常画面と同じデータと履歴を使います。モード切り替えは未保存の本文を保持します。
- アノテーションでは対話生成済みだけを表示し、選択・条件指定がない状態で入ると承認必須の未確認データを最初に表示します。基本の絞り込みはコレクション・レビュー状態・補助タスク・UID検索だけです。「詳細条件」でカテゴリ・到達段階・承認必須のみの条件を追加でき、カテゴリや段階が既に指定されている場合は自動で開きます。「一覧を隠す」で画像と対話に領域を割り当て、「原寸画像を別タブで開く」で小さな文字を拡大確認できます。狭い画面では詳細を引き出しにせず、画像・対話を上下に配置します。
- アノテーションの画像と対話は共通の見出し高さ・本文高さ（標準600px、画面幅800px以下は420px）を使い、左右の開始位置と下端を揃えます。承認・編集・保存・取消は左右共通の上段操作バーにまとめ、編集時は承認ボタンを保存ボタンに切り替えるため本文の位置が変わりません。画像・見出し・一覧に個別の追従表示は使いません。対話は固定高さで上下スクロールし、各発話は全幅のカードとして表示します。各編集欄は本文の長さと画面幅に応じて自動伸縮します。補助情報・正解・確認メモはアノテーションへの切り替え時だけ折りたたみます（通常画面では展開）。別データを開くと対話の先頭に戻り、同じ対話の更新や編集切り替えではスクロール位置を保ちます。
- 「対話音声」「アライメント」は個別に開閉できます。初期状態は閉じており、未生成／作成済みのバッジは閉じたまま確認できます。自動更新やデータ切り替えでも開閉状態は維持します。音声欄を閉じると再生を一時停止し、アライメント行から再生する場合は音声欄を自動で開きます。
- 「判定・保存後に次へ」は既定でオフです。有効にすると、承認・却下または修正版保存に成功した場合だけ、現在の絞り込み内で次のデータを開きます。保存に失敗した場合はその場に留まります。前後ボタン、`Alt + ← / →` でも切り替えられ、未保存の本文がある場合は破棄前に確認します。自動更新だけで選択データや編集中の本文を切り替えません。
- 上部の「総音声」で全コレクションの音声 UID 数と総再生時間を確認し、その下で画像付きデータと非画像対話データを分けて工程別の件数を確認します。
- 左側のコレクションとカテゴリを展開し、表示対象を絞ります。一覧はページ単位で読み込むため、全画像を一度にブラウザへ送りません。
- UID を選択すると、画像、話者別の対話、音声プレイヤー、アライメント区間を表示します。
- `前へ` / `次へ` は現在の検索・カテゴリ・工程フィルタを保ったまま移動します。
- 工程バッジは `画像 → 対話 → 音声 → アライメント` の有無を示します。未作成の工程は空欄ではなく、未完了として明示されます。
- 正解注釈を使わず、VLM 自身の画像判断からカウントまたは OCR を含めた対話には `unverified_vlm_visual` が付きます。「承認必須・未確認（要確認）のみ」を選ぶと、`review_required=true` と `review_status=pending` を同時指定し、承認済み・却下済みは除外します。承認済みを見たい場合は認証済みフィルタを選びます。
- 承認必須かどうかと人手認証済みかどうかは別管理です。通常対話・非画像対話も編集・承認でき、未確認でも通常どおり利用可能です。任意で承認すると「認証済み（人手承認）」ラベルが付きます。却下は必須・任意を問わず利用対象から除外し、認証解除（未確認へ戻す）は必須だけ利用保留、通常データは利用可能のままです。
- 承認必須データは、内容と現在の画像に一致する承認があるまでTTSにも進めません。TTS入口と学習用JSONL作成の両方で検査します。既に存在する旧音声は削除しませんが、編集前の音声は学習用JSONLから除外されます。
- 詳細画面では、確認対象の質問・回答を強調表示し、`承認`、`却下`、`未確認へ戻す`を選べます。承認必須データは承認済みだけが次回の学習用 JSONL 作成時に採用され、未確認・却下は除外されます。通常データは未確認でも利用可能ですが、却下すると除外されます。
- `対話を編集`で各発話の本文を編集し、`保存して承認`で人手修正版を保存・承認できます。発話順・話者は維持します。カウントでは対象と正解数、OCRでは読み取り文字も編集し、本文と一致させてください。編集中の自動更新は入力を上書きしません。別タブが先に保存した場合は競合エラーになり、再読み込みが必要です。
- AI事前修正は、承認必須・未確認で人手の操作履歴がない対話だけに表示します。修正案は別ストア `data/curation/ai_dialogue_suggestions.sqlite3` から読み、元の対話・画像のハッシュが一致する場合だけ適用します。「AI事前修正（未承認）」を開くと元の対話・差分・注意点を確認できます。AIの処理だけでは未確認のままで、音声生成・学習には進めません。
- `AI修正案を承認して保存` は画面に表示した修正案の本文・正解情報を、人手編集と同じ方法で保存・承認します。さらに手直しして保存することもできます。先読み後に人手で承認・却下・編集された対話には古いAI案を保存できません。編集中の入力はAI案の追加でも置き換えません。
- AI案の保存時は、承認履歴のファイル排他ロックを取得し、人手操作の有無を再確認してから追記・永続化まで同じロックを保持します。別プロセスで承認・却下・未確認への戻しが先に保存されていれば、本文が同じでもHTTP 409で拒否し、履歴は追加しません。
- 「AI事前確認」の絞り込みで、処理済みかつ人手未確認の対話だけ、またはAIの注意点が残る対話だけを表示できます。新しい修正案が保存されると一覧を更新しますが、開いている対話や編集中の本文は置き換えません。
- 修正版と承認は承認履歴の同じ1イベントに追記されます。元の生成JSONLは変更せず、カタログ再構築後も修正版を優先します。`build_speech_dataset.py`も同じ履歴を読み、元JSONLを指定したまま修正版を音声化します。修正版の音声保存UIDには`__revision_<内容IDの先頭16文字>`が付き、古い音声・アライメントを上書きしません。修正後の音声作成・アライメントは別工程であり、保存ボタンだけでは実行しません。
- `make_train_jsonl.py`では修正前の音声を`review_superseded`として除外し、現行修正版の承認・音声・アライメントが揃ってから採用します。保存済みの既存学習用JSONLを遡って変更する処理ではないため、学習開始前に必ず再作成してください。
- `却下`でも元データ・修正版・確認メモは削除しません。「人手確認：却下」のフィルタで後の一括再生成対象を確認できます。一括再生成は別途開始する工程です。
- 「人手確認・認証・再作成」ダッシュボードは、承認必須総数・必須要確認数・認証済み数・編集後の再作成待ち・承認任意の未確認数・却下数を集計します。認証済みの内訳には人手編集数と音声・アライメント完成数、再作成待ちには音声待ち・アライメント待ちを表示します。カードをクリックすると対象へ絞り込みます。対話未生成の画像はレビュー件数に含めません。
- 音声またはアライメントが存在する時点で本文を編集した場合、編集履歴の`human_revision.had_media=true`に記録し、修正版の音声とアライメントが両方揃うまで再作成待ちとして数えます。10秒周期の差分確認で解消します。元々音声がなかったデータは新規音声化の対象であり、再作成待ちには数えません。本文を変更せず保存した場合も認証だけ付け、不要な再音声化を要求しません。
- 承認は UID だけでなく、画像の SHA-256、対話全文、補助タスク情報、生成モデルを含む内容 ID に結び付きます。画像や対話を再生成・変更すると以前の承認は一致しなくなり、自動的に再確認待ちになります。
- `更新` はディスクを再走査してカタログへ反映します。生成ジョブの途中でも、書き込み済みの完全なレコードだけを取り込みます。
- 今後の counting / OCR 音声は、`data/speech*count*/data_stereo`、
  `data/speech*ocr*/data_stereo`、または `data/speech*target*/data_stereo`
  に出力すると自動検出します。各 `dialogue.json` の `source_uid` と
  `task_mode` を使うため、`__task_counting` / `__task_ocr` の保存UIDでも
  元画像・対話へ正しく結合されます。

通常の更新は差分確認です。サーバーは既定で10秒ごとに一度だけ差分を確認し、ブラウザも10秒ごとに軽量な状態APIを確認します。カタログの変更番号が進んだ場合だけ、ダッシュボード・ツリー・現在の一覧を再取得するため、変化がない時に大きな一覧を繰り返し読み込みません。自動更新は `--refresh-interval 0` で停止でき、その場合も「再索引」ボタンで手動更新できます。実行中に次の周期が来ても重複実行はしません。

JSONLが変わらず、既知の出力先へ音声・アライメントだけが追加された場合は、未完了UIDだけを確認して反映します。入力定義を変えた場合や数が明らかに合わない場合だけ、起動時の `--rebuild` または更新 API の `force=true` を使って全再構築してください。更新中も直前のカタログは閲覧できます。

## 承認履歴と安全性

承認・編集保存後は、保存成功を確認してから次のデータの表示を優先します。アノテーションでは次の2件の対話・画像を先読みし、保存後の移動で再利用します（最大3件・30秒、絞り込み別）。画像URLには内容の版を付け、古い画像のキャッシュとの混在を防ぎます。保存した行は直ちに一覧へ反映し、未確認の絞り込みから承認済みを除外します。一覧・ダッシュボード・ツリーの再取得は1秒の待機で連続操作をまとめて非同期更新し、次への移動を待たせません。失敗・競合時は次へ移動せず、内容IDの照合と履歴のfsyncは維持します。

詳細表示・承認・編集保存から30秒以内は、重い定期索引を延期して連続確認を優先します。すでに索引中でも、ファイル走査・SQL処理が操作を検知して中断し、未確定の索引変更をロールバックして保存処理へ譲ります。既存カタログは維持され、途中まで走査した状態を公開しません。操作が落ち着くと次の定期確認で再実行します。手動の「再索引」は待機期限を解除しますが、その後の承認・編集は引き続き優先します。延期されるのはビューアの索引だけで、対話生成・音声合成などは止まりません。承認履歴は即時保存され、ダッシュボードは保存済みカタログから更新されます。集計・詳細・画像パスの解決はWebの応答スレッドを塞ぎません。

2026-11-10の改修前ログでは、約3分の背景走査と競合して編集保存が約139秒待つ例がありました。背景走査中の承認・編集、SQL中断、ロールバック後の承認維持、先読みの再利用、古い応答による画面上書き防止をテストしています。API応答の `Server-Timing: app;dur=...` にはサーバー処理時間（ms）を記録し、ブラウザの転送時間と区別して確認できます。本番データを承認・編集して行う性能テストは実施しません。

ビューアが書き込むのは、再構築可能な SQLite カタログ（既定: `data/.dataset_viewer/catalog.sqlite3`）と、承認・編集履歴 `data/curation/dialogue_review_events.jsonl` だけです。履歴は追記専用で、各内容 ID に対する最新の判断が有効になります。編集イベントは`action=edit_and_approve`で、`revised_record`に修正版全文、`base_fingerprint`に元データの内容ID、`parent_fingerprint`に編集直前の内容IDを保存します。元画像、生成済み対話、音声、アライメントは読み取り専用で扱います。

学習用 JSONL を作る `ssvd/tts/make_train_jsonl.py` は、確認対象のレコードについて内容 ID が完全一致する最新の `approved` のみを通します。さらに Asset Manifest 作成時にも承認証跡を再検査するため、未確認データを誤って学習へ入れた場合は失敗して停止します。メディア API はカタログに登録済みの不透明トークンと種別からだけファイルを解決し、任意パスは受け付けません。ブラウザでの音声シークに必要な HTTP Range に対応しています。

```bash
set -o pipefail

MOZ_DISABLE_CONTENT_SANDBOX=1 .venv-data/bin/python dataset_viewer/tests/browser_layout_probe.py \

```
